Intents

An intent declares what the caller needs. The AIP Runtime decides whether and how to run it — the server keeps the final say.

v0.4.0beta Updated 2026.10.06 Edit this page View as Markdown

Most applications re-implement the same backend endpoints again and again. In AIP, the caller expresses the data and action it needs as an intent, and the AIP Runtime runs it inside the contract the server allows. You don't add an API per screen — you declare what the screen needs.

Declaring an intent Section link: Declaring an intent#

Declare the intent next to the code that uses it. The same intent can be written in TypeScript or Python; pick a language once and every example on the site follows.

// orders.intent.ts — illustrative syntax
export const listMyOrders = intent({
  read: "orders",
  where: { owner: "$actor" },
  limit: 20,
});
# orders_intent.py — illustrative syntax
list_my_orders = intent(
    read="orders",
    where={"owner": "$actor"},
    limit=20,
)

Install the SDK first. Copying the command leaves the $ prompt out.

Who decides Section link: Who decides#

The caller is free to ask; the server keeps the authority to run. Every intent passes the permission policy before the Runtime executes it, and the policy sees the authenticated actor — never a value the caller sent.

Request flow Section link: Request flow#

Warning

Never trust an actor id sent by the caller. The policy reads the actor from the verified session.

Specification Section link: Specification#

Spec

Intent request

beta aip.intent/v1
name
Stable identifier. Lowercase, dot-separated.
input
Values the caller provides. Validated before the policy runs.
actor
Resolved by the server from the session. Never part of input.

The Runtime MUST evaluate the permission policy before executing an intent. A policy SHOULD be deterministic for the same actor and input. The caller MAY retry a denied intent only after its session changes.
